# Аудит проекта — 2026-04-04

## Что проверено
- полный pytest-baseline проекта;
- повторный deep-review ручного `/api/v1/sentiment` и release-package integrity;
- повторный deep-review sentiment ingestion, blended/global aggregation и end-to-end `collect_sentiment_once()`;
- целостность README / docs / env-reference;
- fail-safe поведение alerting-контура;
- устойчивость outcome-labeling к нечисловым cost-параметрам;
- smoke-компиляция Python-модулей;
- повторная сборка поставочного архива после правок;
- deep-review outcome-labeling при malformed/legacy `params_json`;
- повторная проверка feature-layer на прямой вызов с poisoned OHLCV/ticker payload'ами;
- сверка консистентности risk limits между bootstrap/API persistence, risk runtime и audit trail;
- deep-review outcome-labeling на poisoned top-level range / kill-switch bounds в grid params.

## Найденные и исправленные проблемы

### 1. README ссылался на неполный пакет документации
**Симптом:** integrity-тест ожидал наличие `docs/audit_2026-04-04.md`, но файл и ссылка в README отсутствовали.

**Риск:** поставка выглядела завершённой, хотя формально документированный аудит ревизии отсутствовал; baseline тестов падал.

**Исправление:** добавлен этот файл и ссылка на него в README.

### 2. Alerting мог уронить цикл на битой health-строке
**Симптом:** `check_and_alert()` обращался к `s["status"]` напрямую.

**Риск:** одна частично повреждённая или legacy health-запись превращала вспомогательный контур оповещений в источник падения recommender-цикла. Это противоречит принципу fail-safe observability: деградация диагностики не должна убивать основной runtime.

**Исправление:** статус теперь нормализуется через безопасный helper. Не-dict и неполные строки больше не вызывают `KeyError`; они учитываются как «не ok», но не ломают цикл.

### 3. Outcome-labeling мог тихо получить `NaN/inf` из cost_model
**Симптом:** `_extract_cost_components()` принимал любые `float(...)`, включая `NaN/inf`.

**Риск:** нечисловая стоимость могла протечь в `_net_return`, grid-outcome и downstream calibration diagnostics, что создавало бы ложные/нефинитные `ret` и ухудшало целостность историки качества модели.

**Исправление:** добавлена finite-нормализация execution/funding cost с безопасным fallback.

### 4. Sentiment ingestion мог ложно симулировать extreme risk-off на битом upstream payload
**Симптом:** в sentiment-контуре часть веток брала внешние значения через прямой `float(...)` или без фильтрации при blended/global combine. При `NaN/inf` из внешнего источника итоговый `clamp` мог фактически увести сигнал к нижней границе или отравить общий расчёт.

**Риск:** один битый ответ внешнего sentiment-source мог создать фиктивный медвежий bias по символу или по всему рынку. Для recommendation engine это опаснее обычного отсутствия сигнала: система видит не «нет данных», а ложный strong risk-off.

**Исправление:** Fear & Greed теперь пропускается при non-finite payload, а blended/global combine учитывают только валидные source rows. Невалидная velocity нормализуется к нейтральному значению, poisoned source block больше не отравляет весь blended/global output.

### 5. Ручной `/api/v1/sentiment` принимал пробельный `key` и мусорные теги
**Симптом:** API принимал `key="   "` и писал его в БД как отдельную series, а список `tags` сохранял как пришёл, включая пустые строки и дубликаты.

**Риск:** оператор мог случайно создать бессмысленные sentiment-ключи и «зашумить» audit trail. Это ухудшает целостность ручных данных: GET-фильтры и визуальный анализ показывают уже не бизнес-сущности, а артефакты ввода.

**Исправление:** перед записью API теперь жёстко нормализует `scope/key`, отвергает пустой `key` с `422`, а `tags` обрезает по краям и дедуплицирует с сохранением порядка.

### 6. Не хватало smoke-покрытия на release-пакет как единый артефакт
**Симптом:** были точечные integrity-проверки, но не было общего smoke-test'а, который одновременно проверяет README, `.env.example`, audit markdown и операторские `docx/pdf`.

**Риск:** поставка могла формально проходить unit/regression baseline, но содержать расходящийся пакет документации: README ссылается на одно, в архиве лежит другое, `.env.example` молчит про критичные operational knobs.

**Исправление:** добавлен release smoke-test, валидирующий наличие и перекрёстные ссылки на `docs/audit_2026-04-04.md`, `instrukciya_operatora_bybit_recommender.docx`, `instrukciya_operatora_bybit_recommender.pdf`, а также ключевые строки `.env.example`.

### 7. Sentiment blending и global combine падали на недиктовых poisoned payload-блоках
**Симптом:** `blend_per_symbol()`, `global_market_momentum_point()` и `combine_global_sentiment()` предполагали, что каждый source block — это dict. Если адаптер или legacy-path возвращал строку/список вместо dict, расчёт падал на `.get(...)`.

**Риск:** один битый source payload мог сорвать весь sentiment-cycle, а вместе с ним и downstream recommendation bias по символам/рынку. Это уже не просто потеря одного источника, а отказ всего sentiment-контура.

**Исправление:** добавлен централизованный helper для пропуска недиктовых payload'ов; blended/global momentum/combine теперь fail-open игнорируют poisoned blocks и продолжают считать по валидным источникам.

### 8. Один битый Reddit-post мог убить sentiment по всему символу
**Симптом:** `fetch_reddit_sentiment()` обрабатывал posts в одном try-блоке на весь символ. Если один элемент `children` был строкой/поломанным объектом, весь symbol выпадал из результата.

**Риск:** частично испорченный Reddit upstream payload создавал ложное «нет данных по символу», хотя соседние посты были валидны. Для blended sentiment это давало ненужную потерю сигнала и неустойчивость к деградации внешнего API.

**Исправление:** poisoned post теперь отбрасывается локально, а валидные соседние посты продолжают участвовать в оценке; дополнительно `collect_sentiment_once()` нормализует типы return payload'ов от source-adapter'ов и не падает на мусорном ответе одного источника.

### 9. Legacy JSON неправильной формы мог ломать operator/API слой уже после чтения из БД
**Симптом:** часть decode-путей использовала generic `json.loads(..., default)` и честно возвращала *любую* форму данных. Если в legacy-строке БД вместо object/list ожидаемого типа лежали строка, число или массив не той структуры, API мог вернуть `params/reasons/state/meta/details` в неожиданной форме. Отдельно `/api/v1/status` и `/metrics` зависели от того, что `app_config` содержит именно dict.

**Риск:** это классический integrity-bug поставки: happy-path тесты зелёные, но одна битая historical/app_config запись роняет UI, status endpoint или downstream-отрисовку деталей рекомендации/бота. Для операторского продукта такой дефект особенно неприятен, потому что ломается не inference, а наблюдаемость и аудит в момент разбора инцидента.

**Исправление:** добавлены shape-aware JSON helper'ы (`dict`/`list`/`list[dict]`/`list[str]`), и все operator-facing decode-paths теперь fail-open возвращают нормализованный payload ожидаемой формы. `status`, `metrics`, `recommendations`, `bots`, `trades`, `sentiment`, `decisions` и duplicate-detection больше не зависят от того, что legacy JSON идеально типизирован.

### 11. Outcome-labeling падал на испорченных grid-параметрах рекомендации
**Симптом:** `_grid_outcome()` напрямую приводил `grid_spacing_pct` и `grid_levels` через `float(...)` / `int(...)`.

**Риск:** одна legacy/manual запись с `"bad"`, `NaN` или иным мусором в `params_json` роняла весь цикл `compute_outcomes_once()`. В результате останавливалась не только разметка конкретного rec, но и весь downstream calibration/update pipeline.

**Исправление:** добавлена безопасная нормализация grid-параметров с finite/default-bound semantics. Теперь corrupted rec деградирует к conservative default, а outcome-cycle продолжает работу.

### 13. Risk limits в БД могли расходиться с реально применяемыми runtime-ограничениями
**Симптом:** bootstrap и `POST /api/v1/risk/limits` сохраняли в `risk_limits` сырой payload как пришёл, а risk-runtime нормализовал тот же набор лимитов уже только на чтении через clamp/default semantics.

**Риск:** оператор видел в audit/БД одну конфигурацию лимитов, а движок фактически работал по другой. Например, `max_symbol_bots=0` или строковый мусор в `max_concurrent_bots` сохранялись как есть, но `/api/v1/risk/status` и execution-gate уже применяли нормализованные значения. Это дефект целостности управления риском: source of truth раздваивается между persistence и runtime.

**Исправление:** добавлена каноническая нормализация `effective limits`; bootstrap и mutating API теперь сохраняют и возвращают уже нормализованный набор ключей. В decision log дополнительно фиксируется и `raw_limits`, чтобы оператор не терял исходный payload запроса.

### 14. Poisoned top-level range bounds могли тихо отключать penalties grid outcome-labeling
**Симптом:** `_grid_outcome()` приводил `price_range_lower/upper` и kill-switch bounds через голый `float(...)`. Строки вида `"NaN"` / `"Infinity"` не падали, а превращались в non-finite числа, после чего range/kill-switch блоки переставали участвовать в расчёте.

**Риск:** partially corrupted `params_json` искажал outcome-labeling не аварией, а хуже — тихой сменой экономики разметки. Историческая grid-статистика могла выглядеть мягче реальности, потому что range occupancy и kill-switch breach penalties фактически выключались poisoned top-level полями.

**Исправление:** ценовые границы теперь принимаются только как положительные finite-значения; при poisoned top-level payload outcome-layer корректно откатывается к валидным границам из `trade_plan.levels.range` и `trade_plan.levels.kill_switch`.

### 12. Feature-layer доверял логической корректности бара только DB-слою
**Симптом:** `compute_features_from_ohlcv()` фильтровал non-finite и часть impossible candles, но принимал бар с `close > high` или `close < low`, если функция вызывалась напрямую в обход `db.get_latest_ohlcv()`.

**Риск:** один poisoned внешний OHLCV-row мог исказить ATR/returns/range-score и дальше протечь в scorer, LLM payload и operator-details. Дополнительно `liquidity_tier()` трактовал `NaN/inf` turnover как реальную ликвидность (`micro/high`) вместо состояния `unknown`.

**Исправление:** feature-layer теперь сам отбрасывает логически невозможные свечи, а poisoned `turnover24h` нормализуется к `unknown` и не создаёт ложных liquidity-veto/allow сигналов.

### 10. Mutating API принимал пустые audit-ключи там, где это разрушает смысл журналирования
**Симптом:** `POST /api/v1/risk/limits` принимал пробельный `version`, а trade API позволял явный `trade_id="   "`.

**Риск:** в БД могли появляться бессмысленные audit-идентификаторы и версии без семантики. Это ухудшает разбор инцидентов и делает history/идемпотентность менее прозрачными.

**Исправление:** добавлена строгая нормализация operator-input: пустой `version` и явный пустой `trade_id` теперь отклоняются с `422`, а optional operator/reason поля аккуратно trim'ятся без записи пробельного мусора в audit trail.

- CoinGecko momentum fail-open отрабатывает сетевой сбой без падения sentiment-thread;
- alerting устойчив к недиктовым элементам в health payload;
- outcome-cost extraction нормализует `NaN/inf` к безопасным finite значениям;
- Fear & Greed источник игнорирует non-finite upstream payload;
- blended per-symbol sentiment пропускает poisoned source blocks и сохраняет finite output;
- blended/global sentiment игнорируют недиктовые source blocks вместо падения на `.get(...)`;
- один битый Reddit-post больше не выбрасывает весь symbol из результата;
- `global_market_momentum_point()` использует только валидные per-symbol momentum rows;
- `collect_sentiment_once()` fail-open переживает мусорные return payload'ы отдельных source-adapter'ов;
- global sentiment combine игнорирует битые source rows вместо отравления итогового market pulse;
- release smoke-check защищает консистентность README / docs / `.env.example` как одного поставочного артефакта.

## Логические выводы по ревизии
- Архитектура проекта в целом консистентна: есть разумное разделение data/inference/control/audit слоёв.
- Критичный execution-risk сознательно вынесен за пределы проекта; для recommendation engine это корректно отражено в документации.
- Основные найденные проблемы были не в «математике альфы», а в краевых сценариях целостности runtime, historical payloads и поставки. Именно такие дефекты чаще всего выстреливают в production раньше, чем базовая торговая логика.

## Рекомендации на следующую ревизию
- расширить release smoke-test до проверки содержательной синхронизации operator docs с README при следующих ревизиях;
- добавить отдельный stress/regression набор на partially corrupted trade/bot state payload'ы в risk and lifecycle APIs, чтобы те же fail-open гарантии были симметричны всем operator-facing сущностям;
- при переходе к live-эксплуатации держать отдельный paper/staging прогон с записью trade rows, иначе часть risk/control механики останется недонагруженной реальными данными.
